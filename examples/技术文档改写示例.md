# 技术文档改写示例

以下均为构造的示例。原文提供了术语的含义和处理方式，改写不推断额外的实现细节。

## 示例一：字段名要配中文说明

原文：

```markdown
用例中的 checks 字段只引用 check_id。其中，checks 表示检查项，check_id 表示检查项编号。
```

改写：

```markdown
用例里的检查项 `checks` 只引用检查项编号 `check_id`。
```

原因：读者先看到中文含义，也能找到准确字段名。编号是否已经定义，原文没有说明，改写不补这个前提。

## 示例二：保留必要工程术语

原文：

```markdown
这段逻辑需要支持幂等，即重复提交同一请求不会重复写入；支持回注，即把结果写回原系统；支持干跑，即只检查流程、不真实发送消息；发生异常时停止后续处理，作为兜底措施。
```

改写：

```markdown
这段逻辑需要支持重复提交同一请求不会重复写入，也就是幂等；还需要把结果写回原系统，支持只检查流程、不真实发送消息的模式。发生异常时停止后续处理。
```

原因：保留准确约束，按读者需要解释术语。所有处理方式均来自原文；面向熟悉这些术语的研发读者，也可以保留原句。

## 示例三：把实现词换成可理解动作

原文：

```markdown
主流程先整理可核对的事实，再触发被测流程；随后在消息真实发送前拦截，并在异常时停止后续处理。文档将这些步骤称为“结构化事实预处理、触发被测链路、出站截获和硬兜底”。
```

改写：

```markdown
主流程先整理可核对的事实，再触发被测流程。随后在消息真实发送前拦截；如果发生异常，就停止后续处理。
```

原因：保留操作顺序和异常处理方式，去掉重复的术语说明。原文没有提到高风险动作或人工复核，改写不增加这些机制。
